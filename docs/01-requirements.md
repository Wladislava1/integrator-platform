Номера FR, NFR и US не меняются до конца семестра. На них ссылаются диаграммы, а в следующих работах — код и тесты.

## 1. О приложении

Связь ID — одна учётная запись физического лица на платформе. Человек регистрируется и входит один раз. Каталог показывает продукты, которые пользуются этой учётной записью. Продукт не заводит свой пароль: он спрашивает платформу, кто вошёл, и получает идентификатор, имя и почту.

На момент версии 1.1 уже работают регистрация, вход, выход, каталог из пустых слотов, профиль и тема. В этом семестре каталог нужно доработать: в нём появляется подключённый тестовый продукт. Сам тестовый продукт — отдельное приложение, не этот репозиторий. Он подключает вход Связь ID и показывает имя и почту вошедшего. Запрос «кто вошёл» описан в FR-8, проверка на тестовом продукте — в FR-9. В коде этого ещё нет.

Роли:

| Роль | Кто это |
|------|---------|
| Физическое лицо | Человек, который регистрируется, входит, смотрит каталог и ведёт свой профиль |
| Продукт | Внешняя система в каталоге. Своих пользователей не хранит, узнаёт личность у платформы |
| Тестовый продукт | Простое отдельное приложение для проверки. Названия пока нет. Подключает тот же вход и показывает имя и email |

Термины:

| Термин | Значение |
|--------|----------|
| Пользователь | Физическое лицо, заведённое на платформе |
| Сессия | Факт входа. Сейчас это JWT в cookie браузера на 7 дней. К концу семестра срок и состояние сессии хранятся в базе |
| Продукт | Система, которая стоит в каталоге и запрашивает личность пользователя |
| Тестовый продукт | Отдельное приложение, на котором в этом семестре проверяется подключение входа |
| Настройки | Выбор темы этого пользователя: светлая, тёмная или как в системе |

Чужой поставщик входа в этот семестр не входит. Платформа сама выпускает сессию.

## 2. Требования к функционалу

Приоритет: обязательно в этом семестре, желательно, потом. Состояние: уже есть, нужно доработать, нужно сделать.

### FR-1

Физическое лицо может зарегистрировать учётную запись Связь ID: фамилия, имя, отчество, email, пароль и повтор пароля.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | уже есть |
| Признак выполнения | После верных данных система создаёт пользователя, пускает его в каталог и не показывает пароль открытым текстом |

### FR-2

Физическое лицо может войти по email и паролю.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | уже есть |
| Признак выполнения | Верная пара email и пароль открывает каталог, сессия становится активной на 7 дней |

### FR-3

Физическое лицо может выйти из платформы.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | уже есть |
| Признак выполнения | После «Выйти» защищённые страницы снова требуют вход |

### FR-4

Физическое лицо может открыть каталог и увидеть в нём подключённый тестовый продукт.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | нужно доработать |
| Признак выполнения | После входа открывается каталог. Пустые слоты уже есть. Работа закончена, когда среди них видна карточка тестового продукта и из неё можно перейти в это отдельное приложение |

### FR-5

Физическое лицо может смотреть и менять личные данные: фамилию, имя, отчество, email, телефон, пол, адрес и дату рождения.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | уже есть |
| Признак выполнения | Сохранённые поля видны при следующем открытии профиля |

### FR-6

Физическое лицо может сменить пароль, указав текущий пароль, новый пароль и повтор нового.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | уже есть |
| Признак выполнения | Старый пароль больше не входит, новый входит |

### FR-7

Физическое лицо может выбрать тему: светлая, тёмная или как в системе.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | уже есть |
| Признак выполнения | После переключения в шапке оформление страниц соответствует выбранной теме и сохраняется для этого пользователя |

### FR-8

Продукт может спросить у платформы, какое физическое лицо сейчас вошло, и получить его идентификатор, имя и email.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | нужно сделать |
| Признак выполнения | `GET /api/identity` с действующим токеном сессии отвечает 200 и телом `{ id, fullName, email }`. Пароля и хеша в ответе нет. Без действующего токена ответ 401, профиля в теле нет, продукт свою учётную запись не создаёт |

Токен — тот же JWT, который платформа выдаёт при входе. Продукт получает его, когда пользователь открывает продукт из каталога, и передаёт в заголовке `Authorization: Bearer`.

### FR-9

Тестовый продукт может подключить вход Связь ID и показать физическому лицу его имя и email.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | нужно сделать |
| Признак выполнения | Человек входит в Связь ID и открывает тестовый продукт из каталога. Отдельное приложение вызывает FR-8 и показывает то же имя и email, что в профиле. Своей регистрации у продукта нет. Без сессии имя и email не показываются |

Тестовый продукт не хранится в этом репозитории. Название приложения в требовании не фиксируется.

### Ограничения

#### NFR-1

Платформа открывается в актуальном браузере на широком экране и на ширине 375 px, отдельную программу ставить не нужно.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | уже есть |
| Признак выполнения | Страницы входа, каталога и профиля читаются на ширине окна 1280 px и 375 px |

#### NFR-2

Повторное открытие страницы входа при запущенном приложении занимает не больше 2 секунд.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | уже есть |
| Признак выполнения | Повторный `GET /login` на `http://localhost:3000` завершается быстрее 2 секунд. Первая компиляция страницы в этот замер не входит |

#### NFR-3

Пароль хранится только как хеш bcrypt. Скрипт страницы не может прочитать cookie сессии.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | уже есть |
| Признак выполнения | В хранилище пользователей есть `passwordHash` и нет исходного пароля. У cookie `svyaz_id_token` установлен HttpOnly |

#### NFR-4

К концу семестра пользователи и сессии хранятся в PostgreSQL.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | нужно сделать |
| Признак выполнения | Регистрация создаёт строку пользователя, вход создаёт строку сессии с `expires_at`. Файл `.data/users.json` больше не источник данных. Схема лежит в `src/db/schema.sql` |

#### NFR-5

Файл пользователей и секрет подписи сессии не попадают в репозиторий.

| | |
|---|---|
| Приоритет | обязательно в этом семестре |
| Состояние | уже есть |
| Признак выполнения | `.data/` отсутствует в git, в репозитории есть `.env.example` и нет заполненного `.env` |

## 3. Пользовательские сценарии

Схема: я как роль имею данные и состояние, делаю шаги, получаю результат. У каждого сценария указаны вход и выход. Три ключевых сценария содержат пример с конкретными значениями и отдельный ход с неверными данными.

### US-1. Регистрация

Требование: FR-1. Ключевой сценарий.

Я как физическое лицо не имею учётной записи. Ввожу фамилию, имя, отчество, email, пароль и повтор пароля. Получаю учётную запись и активную сессию, меня переносит в каталог.

Вход: фамилия, имя, отчество, email, пароль, повтор пароля. Учётной записи с этим email ещё нет.

Выход: пользователь сохранён, пароль лежит только как хеш, установлена cookie `svyaz_id_token`, открыт каталог.

Пример. Фамилия `Иванова`, имя `Мария`, отчество `Сергеевна`, email `maria.ivanova@example.com`, пароль `Svyaz-26`, повтор `Svyaz-26`. Ответ `201`, в теле пользователь с этим email и ФИО «Иванова Мария Сергеевна», без поля пароля. Следующая страница — каталог.

Неверные данные. Повтор пароля `Svyaz-99` при пароле `Svyaz-26`. Ответ `400`, на форме текст «Пароли не совпадают». Пользователь не создаётся, cookie не ставится, каталог не открывается.

### US-2. Вход

Требование: FR-2. Ключевой сценарий.

Я как физическое лицо имею уже созданную учётную запись и ещё не вошло в этом браузере. Ввожу email и пароль. Получаю активную сессию на 7 дней и каталог.

Вход: email и пароль существующего пользователя. Сессии в браузере нет.

Выход: cookie `svyaz_id_token`, состояние сессии «активна», открыт каталог.

Пример. Email `maria.ivanova@example.com`, пароль `Svyaz-26`. Ответ `200` и пользователь в теле. Каталог открывается без повторного ввода пароля, пока не пройдёт 7 дней и пользователь не нажмёт «Выйти».

Неверные данные. Пароль `wrong-pass` при том же email. Ответ `401`, на форме текст «Неверный email или пароль». Cookie не ставится, каталог не открывается, пароль в хранилище не меняется.

### US-3. Выход

Требование: FR-3.

Я как физическое лицо имею активную сессию. Нажимаю «Выйти». Сессия этого браузера завершается, снова видна страница входа.

Вход: cookie действующей сессии.

Выход: cookie удалена, `GET /api/auth/me` отвечает `401`, каталог без нового входа не открывается.

### US-4. Каталог

Требование: FR-4.

Я как физическое лицо имею активную сессию. Открываю каталог. Вижу карточку тестового продукта и перехожу в него.

Вход: активная сессия и подключённый тестовый продукт.

Выход: в каталоге есть карточка тестового продукта, переход открывает отдельное приложение. Новая учётная запись при этом не создаётся. Пустые слоты, которые уже рисуются, остаются на странице.

### US-5. Личные данные

Требование: FR-5.

Я как физическое лицо имею активную сессию. Меняю поля профиля и сохраняю. При следующем открытии вижу новые значения.

Вход: активная сессия и новые значения полей.

Выход: у того же пользователя обновлены только переданные поля.

### US-6. Смена пароля

Требование: FR-6.

Я как физическое лицо имею активную сессию и знаю текущий пароль. Ввожу текущий пароль, новый и повтор. Дальше вход выполняется новым паролем.

Вход: текущий пароль, новый пароль не короче 8 символов и с хотя бы одной цифрой, повтор нового пароля.

Выход: хеш пароля заменён. Прежний пароль даёт «Неверный email или пароль».

### US-7. Тема

Требование: FR-7.

Я как физическое лицо имею активную сессию. В шапке выбираю светлую, тёмную тему или «как в системе». Оформление меняется и остаётся у этого пользователя.

Вход: одно из значений `light`, `dark`, `auto`.

Выход: у пользователя сохранена выбранная тема, страницы отображаются в ней.

### US-8. Кто вошёл

Требование: FR-8. Ключевой сценарий. В коде конечной точки ещё нет, ниже описан ожидаемый результат.

Я как продукт не храню пароли физических лиц. Получаю токен сессии, когда пользователь открывает меня из каталога, и вызываю `GET /api/identity` с заголовком `Authorization: Bearer <токен>`. Получаю идентификатор, имя и email либо отказ.

Вход: токен сессии Связь ID.

Выход при действующей сессии: `200` и `{ id, fullName, email }`. Своя учётная запись в продукте не создаётся.

Пример. Токен сессии пользователя `maria.ivanova@example.com`, выданной при входе из US-2. Ответ `200`: `id` этого пользователя, `fullName` = `Иванова Мария Сергеевна`, `email` = `maria.ivanova@example.com`. Полей `password` и `passwordHash` нет.

Неверные данные. Заголовок `Authorization` не передан. Ответ `401`, тело `{ "error": "Требуется вход" }`. Полей `id`, `fullName` и `email` нет. Продукт не создаёт пользователя и не открывает его данные.

### US-9. Тестовый продукт показывает имя

Требование: FR-9. В коде ещё нет, ниже описан ожидаемый результат.

Я как тестовый продукт не храню пароль физического лица. Человек открывает меня из каталога Связь ID и приносит токен сессии. Я вызываю `GET /api/identity` и показываю имя и email.

Вход: токен сессии и отдельное приложение тестового продукта.

Выход: на экране продукта видны имя и email из платформы. Своя учётная запись не создаётся.

Пример. После входа `maria.ivanova@example.com` тестовый продукт показывает «Иванова Мария Сергеевна» и `maria.ivanova@example.com`.

Неверные данные. Человек открывает тестовый продукт без входа в Связь ID. Имя и email на экране не появляются, продукт сообщает, что нужен вход, и никого не регистрирует.
